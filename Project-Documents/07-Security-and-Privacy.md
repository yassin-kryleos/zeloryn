# Security and Privacy

## 1. Security Posture

Kryleos Forge is powerful because it can read files, write files, run commands, and call external AI providers. Those same capabilities create security responsibilities.

## 2. Key Risks

- API keys stored insecurely.
- Sensitive workspace files sent to third-party AI providers.
- Unsafe shell command execution.
- Silent execution of AI-proposed shell commands without user review.
- Stale or spoofed command approval messages.
- Ambiguity between local host execution and remote container execution simulation.
- Accidental publishing of private files.
- Workspace path traversal bugs.
- Prompt injection through project files.
- Sync leakage of sensitive configuration.
- Tier-gate bypasses for sync, RBAC, or simulated premium features.

## 3. Existing Mitigations

- Workspace sandbox resolves paths relative to the selected root.
- AI-proposed shell commands require explicit user approval before execution.
- Pending command approval/cancellation is represented in the terminal UI.
- Active workflows can be interrupted with a stop control.
- Stale command approvals are rejected when their `commandId` does not match the active pending command.
- Active command child processes are tracked and terminated during graceful abort.
- Path access outside the workspace should be rejected.
- Common generated or sensitive folders/files are ignored in some graph/sync flows.
- User must configure provider credentials.
- Custom agents/skills are local workspace artifacts.
- Free-tier sync is blocked; Solo and higher tiers are required for cross-device sync.
- Local vs remote-container execution mode is surfaced through tier-aware shell banners.

## 4. Required Production Improvements

### Secure Credential Storage

Move API keys and OAuth tokens out of plain JSON/localStorage and into OS-backed secure storage:

- Windows Credential Manager
- macOS Keychain
- Linux Secret Service

### Explicit Provider Disclosure

When sending workspace context to hosted models, clearly tell users that code/content may leave their machine.

### Command Execution Controls

Before public release:

- Add command allow/deny policies.
- Show commands before execution when generated by AI.
- Require confirmation before running proposed commands.
- Keep stale command approval rejection covered by tests.
- Make cancellation and abort events visible in the log.
- Add timeout and output-size limits.
- Decide whether to wire browser-side cryptographic approval signatures into the UI, or remove unused signing expectations from the command approval design.

### Workspace Rule Safety

`.cursorrules` and `.cursor/rules` improve compatibility but can also contain prompt injection or unsafe instructions. Rule contents should be treated as workspace developer context, not as absolute authority over security policies.

Security rules:

- Workspace rules must not override sandbox boundaries.
- Workspace rules must not bypass command approval.
- Workspace rules must not disable secret scanning, publish checks, or tier gates.

### File Publish Safeguards

Before publishing Gists or syncing files:

- Warn if `.env`, secrets, tokens, or private keys are detected.
- Ask for confirmation.
- Show the target filename and destination.

### Sync Hardening

Before production:

- Replace simulated auth with real auth.
- Encrypt sync data in transit and at rest.
- Define user deletion/export flows.
- Add server-side authorization for every sync request.

### Tier and Billing Hardening

Before production:

- Replace mocked `/api/auth/subscribe` upgrades with a real billing provider.
- Server-enforce tier gates rather than relying on UI indicators.
- Log and audit tier changes.
- Ensure Agency/Team RBAC permissions are enforced on every push/sync route, not only displayed.

### Remote Execution Hardening

Before marketing remote execution as production-ready:

- Replace simulation banners with real isolated container infrastructure.
- Prevent Free/Solo/Solo Plus users from accidentally assuming local host execution is isolated.
- Add execution environment labels to logs and exported artifacts.

## 5. Privacy Principles

- Local-first by default.
- No implicit publishing.
- No hidden workspace uploads.
- Make provider routing visible to the user.
- Make account and sync status explicit.
