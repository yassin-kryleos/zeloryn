# Security, Privacy, and Threat Model

## Security Posture

Kryleos Forge is powerful because it can read files, edit files, run commands, call models, and coordinate companion devices. Security must be designed as a core product layer, not as polish.

## Protected Assets

- Workspace files.
- Source code and Git history.
- Provider API keys.
- GitHub tokens.
- Sync/account tokens.
- Billing webhooks/secrets.
- Pairing codes/secrets.
- Mobile device private keys.
- Execution traces and logs.
- Tool registry, MCP server configs, and tool audit logs.
- Swarm lane state and learning memory.
- User plans and project descriptions.

## Trust Boundaries

```text
Desktop renderer -> local backend
Local backend -> workspace filesystem
Local backend -> model providers
Local backend -> Tool API Gateway -> built-in tools
Tool API Gateway -> MCP servers and external APIs
Local backend -> Swarm Orchestrator -> Agent Orchestrator
Local backend -> Learning Engine -> local .kryleos learning memory
Local backend -> billing providers
Companion device -> companion WebSocket
Preview iframe/webview -> untrusted local/public content
```

## Core Controls

### Local Session Authentication

- Local REST requires a process-scoped session secret.
- Secret must be at least 32 characters when auth is required.
- Secret is generated by Electron main and delivered to the renderer only through a typed preload API.
- Compare secrets with timing-safe equality.
- Do not expose the secret to companion clients.
- CORS and loopback binding are not sufficient by themselves because other local processes can call localhost.
- Health endpoints must not expose session, secret, or capability-token details.

### Electron Shell Hardening

- `contextIsolation` must be enabled.
- `nodeIntegration` must be disabled in renderer windows.
- Preload exposes narrow typed APIs only.
- IPC payloads are schema-validated.
- Untrusted navigation is denied.
- `window.open` and external URL opening are gated.
- Production CSP is restrictive; development CSP is explicitly separated.
- Preload/backend crash paths show diagnostics instead of blank windows.

### Workspace Boundary

- Resolve real paths.
- Reject file operations outside workspace.
- Allow multi-repo roots only through explicit whitelisting.
- Do not follow symlinks outside allowed roots.
- Keep delete/revert behavior conservative.

### Command Approval

- All AI-proposed shell commands require user approval.
- Approval must include active command ID.
- Reject stale approval IDs.
- Mark destructive commands.
- Stop workflow must reject pending approvals and terminate tracked child processes.

### Tool API Governance

- All model-callable tools are registered with schema, permission, scope, tier, and approval policy.
- Provider-native tool calls, MCP tools, custom skills, and text fallback actions all pass through the same gateway.
- Tool arguments are validated before execution.
- Tool outputs are sanitized before returning to models.
- External and MCP tool results are treated as untrusted evidence.
- Write, execute, network, and admin tools require explicit policy and audit records.
- Remote companion approval is allowed only for tools marked `remoteApprovalAllowed`.
- Tool invocation logs redact secrets and credential references.

### Swarm and Learning Governance

- Swarm workers cannot bypass the Tool API Gateway.
- Swarm writes, commands, Git mutations, network calls, and admin actions remain approval-gated.
- Stop workflow aborts every active swarm lane.
- Learning is local-only in V1.
- Learning recommendations are suggest-only until user approval.
- Learning memory must store evidence references, not raw secret-bearing context.
- Secret scan blocks credentials from learning memory.
- Rejected learning recommendations cannot be re-applied automatically.
- Rollback disables approved patterns.

### Companion Security

- Pairing code is short-lived.
- Pairing secret is available only through loopback desktop UI/QR.
- Wrong pairing attempts are rate-limited/locked out.
- Devices register public keys and receive device tokens.
- State-changing messages require:
  - Registered device.
  - Signature.
  - Fresh nonce.
  - Valid timestamp.
  - Correct command/task/session ID.
- Device revocation closes active connections.

### Provider Privacy

- Hosted providers receive prompts and selected context.
- Show one-time disclosure per hosted provider.
- Zero Egress blocks non-local providers in backend routing.
- Zero Egress also blocks network tools and remote MCP calls that would send workspace data out.
- Ollama/local models are allowed offline.
- PII redaction can be applied before outbound model calls where enabled.

### Secret Storage

- API keys must not be in localStorage.
- Use Electron safeStorage or encrypted backend storage.
- Encrypted DB key must be per install, not hardcoded.
- Mobile device identity must use secure storage.

### Webhook Security

- Stripe webhooks require signature verification except mock development.
- Razorpay webhooks require signature verification except mock development.
- Production must fail closed if mock keys are configured.

### Secret Scanning

Generated docs/workflow exports must be scanned for:

- OpenAI keys.
- Anthropic keys.
- Google API keys.
- AWS keys.
- GitHub tokens.
- Stripe live keys.
- Slack tokens.
- JWTs.
- Private keys.
- Generic password/token assignments.

Block writes/exports unless user explicitly bypasses after warning.

## Threats and Mitigations

### Malicious Web Page Calls Local API

Risk: arbitrary origin tries to access local backend.

Mitigations:

- Origin restrictions.
- Local session header.
- Loopback binding for admin API.
- No wildcard privileged CORS.

### Companion Device Spoofs Approval

Risk: untrusted LAN client approves command.

Mitigations:

- Pairing code and secret.
- Registered device keys.
- Signed messages.
- Nonce replay protection.
- Timestamp checks.
- Device revocation.

### Agent Runs Destructive Command

Risk: model proposes deletion or risky shell operation.

Mitigations:

- Command classification.
- User approval.
- Destructive warning.
- Process tracking and abort.
- Review evidence.

### Path Traversal or Symlink Escape

Risk: file tools access outside workspace.

Mitigations:

- Realpath resolution.
- Parent/child path checks.
- Workspace whitelist only.
- Tests for traversal and symlink containment.

### Hosted Provider Data Leakage

Risk: private code leaves machine unintentionally.

Mitigations:

- Provider disclosure.
- Zero Egress backend enforcement.
- PII redaction.
- Clear model/provider status.

### Secret Leakage in Generated Docs

Risk: LLM-generated docs include secrets from context.

Mitigations:

- Secret scan before write/export.
- Bypass requires explicit user action.
- Avoid sending unnecessary secret-containing files to models.

### Tool Output Prompt Injection

Risk: an MCP server, website, log file, issue, or API response includes instructions that try to override the agent or exfiltrate data.

Mitigations:

- Mark tool output as untrusted context.
- Strip or quote instruction-like content in summaries.
- Run prompt-injection scan on high-risk external output.
- Require explicit user approval before tool output can trigger write, execute, network, or admin actions.

### Malicious or Compromised MCP Server

Risk: an MCP server exposes dangerous tools, lies about outputs, or attempts data exfiltration.

Mitigations:

- New MCP servers are disabled until tested.
- Local stdio MCP discovery is itself execution of local code and must not run automatically for untrusted commands.
- Before first stdio launch, show command, args, working directory, environment summary, and trust impact.
- Prefer manifest/static metadata inspection before process launch when available.
- Discovered tools require allowlisting before use.
- MCP tools cannot access shell/filesystem except through Forge built-ins.
- Tokens are stored as credential references and never exposed to models.
- Per-server disable/revoke controls close active connections.

### Unsafe Custom Skill Execution

Risk: a custom script skill is treated like passive data but can execute arbitrary code.

Mitigations:

- Skill definitions declare permissions and workspace scope.
- Script skills are disabled until reviewed and enabled.
- Script skills execute through the Tool API Gateway, not through direct renderer or model execution.
- Network, shell, filesystem, and admin effects require the same approvals as built-in tools.
- Skill output is untrusted context and cannot trigger follow-up actions without approval.

### Network Tool Exfiltration

Risk: an agent or compromised tool sends workspace contents to an unapproved URL.

Mitigations:

- Destination and payload summary shown before network calls.
- Network tools use `always` approval by default.
- Zero Egress blocks network calls involving workspace data.
- Audit logs record redacted destination and purpose.

### Bad Learning Reinforcement

Risk: failed, unsafe, or prompt-injected output becomes a trusted future pattern.

Mitigations:

- Learn only from evidence-backed signals.
- Treat tool/MCP/web/log output as untrusted.
- Require user approval before learned patterns affect future prompts.
- Exclude rejected, aborted, secret-bearing, and prompt-injection-positive events from positive patterns.
- Keep rollback records.

### Log Leakage or Over-Retention

Risk: logs and traces expose private paths, git remotes, command arguments, provider names, approval IDs, or secrets.

Mitigations:

- Structured logs are redacted before write.
- Provider keys, tokens, pairing secrets, credential references, and secret-like command args are never logged.
- Logs have rotation and local retention defaults.
- Log export runs through sanitizer and user confirmation.
- Crash diagnostics show minimal actionable state, not raw secrets or full private file contents.

### Billing Forgery

Risk: client claims paid tier.

Mitigations:

- Server resolves tier from validated user/license/subscription.
- Webhooks verified.
- Client tier is display-only.
- Feature gates enforced server-side.

## Privacy Modes

### Default Mode

Hosted providers may be used after disclosure. Only referenced or selected context should be sent.

### Zero Egress Mode

- Blocks hosted providers.
- Allows Ollama/local models.
- Blocks remote MCP and network tools that could transmit workspace data.
- Blocks cloud or cross-user learning.
- Shows persistent local-only badge.
- Logs local-only model call status.

### Offline Desktop

Supported with local models and local tools.

### Offline Mobile

Only planning notes are supported offline. Execution requires desktop/provider connectivity.
